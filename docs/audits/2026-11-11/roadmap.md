## 合并与交付方式

- 用窄 PR 优先修继承自 main 的 P0。每片记录固定 base/head、写集、用户影响、回滚命令和复验证据。对 #5 保留原分支作审计基线，从候选分离基础网关、Responses、控制台、其他端点。复用 G0–G4 的断言，不叠加平行实现。
- #6 的安全、目录、转换、Fallback、管理入口拆开。先在候选前置依赖下修，稳定基线落到 main 后建立新的审查差异。用 merge commit 保持真正的堆叠祖先；若取窄切片，用 `cherry-pick -x` 记录来源并核对 diff；不重写共享历史。#4/#2 保留出处，替代片通过后关闭旧入口。
- 每次变更前检查远端 base/head、worktree、未提交内容和同写集进程。合并前对当前 head 与目标合并树分别跑受控验证、保留远端检查结果，按合并 SHA 再运行基础、集成、文档与适用产品验收。测试/最小验证由 gpt-6-luna high 执行，主控负责代码审计及证据裁决。
- 用固定客户端版本和版本升级矩阵验收。目录可解析、双 mock 真客户端、真实官方、真实第三方、Desktop GUI 分开记录。为每项保存时间、环境、SHA、命令、计数、未验范围和证据路径。
- 静态审查覆盖主干风险前，测试通过仍保留合并阻断。合并后的失败用小修补或可审计 revert。生产发布和用户数据操作由单独流程授权。

## 资源、预算及依赖

本轮新增大型安装/下载为零。M0–M2 默认使用现有 Node、浏览器、Codex CLI 与合成数据，上游费用预算 0。M3–M5 默认仍为 0 实际调用，合成报价可验证预留和对账。真实验收若有授权，另列供应商、调用次数、token 上限、每任务与每日限额、价格来源、过期时刻和停止条件。价格、额度或授权未知时保持关闭。新增资源先核 lockfile、本机工具和缓存、其他项目复用、体积和替代方案。 [资源授权规则](https://github.com/xiaomengxizzh/model-gate/blob/6bc6441fc7bf3e620b19af5af3b4d62543b31193/RESOURCE_APPROVAL.md)

主要依赖依次为可复现主干与 CI、端点共用执行策略、Codex 版本化能力与官方授权、UHR 可用的任务 API。registry 本轮失效，跨仓依赖面待恢复后核对。交付先实现单机可信网关和可回滚管理台，再扩展可选 Codex 适配及 UHR 委派。开放平台集成保持与正式支持边界一致。
